# Git Worktree Utilities

Набор утилит для автоматизации работы с **Git Worktrees**. Упрощает создание изолированных окружений для параллельной разработки.

## Единый CLI: `wt`

Все утилиты доступны через единую команду `wt`.

### Команды

| Команда | Алиасы | Описание |
| :--- | :--- | :--- |
| `wt new <name>` | `create` | Создать новую задачу (ветку + папку + setup) |
| `wt list` | `ls` | Показать список активных worktrees (со статусом и ahead/behind) |
| `wt kill <name>` | `rm` | Удалить worktree (`-D` — также ветку, `-y` — без подтверждения, `-f` — разрешить force) |
| `wt setup` | `init` | Настроить/обновить окружение в текущей папке |

### Конфигурация (`.worktree-config`)

При создании (`new`) или настройке (`setup`) worktree скрипт читает файл `.worktree-config` из **основного (main)** репозитория и применяет правила к корню текущего linked worktree, даже при запуске из подпапки. В main worktree `setup` отказывается работать до любых файловых операций и `RUN`.

**Формат файла:**
Каждая строка — это инструкция. Синтаксис: `КОМАНДА АРГУМЕНТ`. Первый пробел разделяет команду и аргумент — поэтому пути с пробелами и многословные `RUN` команды работают корректно.

| Команда | Описание | Пример использования |
| :--- | :--- | :--- |
| `LINK` | Создает симлинк на файл/папку из основного репозитория. (По умолчанию, если команда не указана). | Общие скрипты, конфиги IDE, `.gitignore`. |
| `COPY` | Копирует файл из основного репозитория. Полезно для шаблонов, которые должны быть независимыми в каждом worktree. | `.env`, локальные конфиги базы данных. |
| `RUN` | Выполняет shell-команду в корне worktree в порядке инструкций, в отдельном subshell. | `npm install`, `composer install`. |

> **⚠️ Безопасность.** Строки `RUN` исполняются через `eval` в shell-контексте текущего пользователя. `.worktree-config` — это конфигурация уровня доверия `Makefile`: никогда не запускайте `wt setup` в репозитории с непроверенным `.worktree-config`.

> **Существующие файлы (`LINK` / `COPY`).** Записи из `.worktree-config` могут заменять только tracked-файлы и каталоги без локальных изменений, untracked **и ignored** содержимого. Локальные файлы и существующие симлинки (включая dangling) сохраняются; такие операции пропускаются. Записи из `.git/info/exclude` не перезаписывают существующие пути. Цели с gitlink/submodule, вложенной Git-метаинформацией (`.git` или bare-структура `HEAD` + `objects`) либо index-флагами `assume-unchanged` / `skip-worktree` консервативно пропускаются: обычный `git status` не гарантирует сохранность их данных. Проверки Git используют literal pathspecs, чтобы имена вида `:(literal)name` не интерпретировались как команды pathspec. `COPY` сохраняет симлинки, не копирует содержимое их целей.

> **Пути и exclude.** Завершающий `/` у каталога нормализуется в обоих источниках. В `.git/info/exclude` также поддерживается один начальный `/` как привязка к корню (`/build` → `build`). Отсутствующий источник просто пропускается, в том числе `dist/`. Небезопасные/неподдерживаемые exclude-записи и дочерние пути через симлинк пропускаются с предупреждением; например, после ссылки `.idea` запись `.idea/ws.xml` не обрабатывается. Для `.worktree-config` абсолютные пути, компоненты `..`, `.git` и операции через симлинк в родительском каталоге назначения остаются ошибкой.

> **Ошибки setup.** Инструкции выполняются по порядку. При ошибке `RUN`, копирования, создания ссылки/каталога или удаления `setup` немедленно останавливается с ненулевым кодом; уже выполненные шаги не откатываются. Каждый `RUN` запускается в отдельном subshell: его `cd` и `exit` не влияют на следующие инструкции. Успех сложной shell-команды определяется её итоговым статусом (например, для pipeline действуют обычные правила Bash). При ошибке setup команда `wt new` также возвращает ненулевой код и **сохраняет созданные worktree и ветку** для диагностики. Отсутствующий или неисполняемый `wt-setup` также считается ошибкой готовности окружения: `wt new` возвращает ненулевой код, сохраняя worktree и ветку.

### Безопасное удаление

`wt kill <name> --yes` (`-y`) только отключает подтверждение. Dirty/untracked worktree без явного `--force` (`-f`) не удаляется; повторного автоматического удаления с force нет. Для осознанного удаления с потерей локальных данных используйте `wt kill <name> --yes --force`. Без `--yes` подтверждение остаётся обязательным даже с `--force`. Ошибка удаления worktree или ветки (`-D`) возвращает ненулевой код. Отмена пользователем — не ошибка. Успешное удаление detached worktree с `-D` возвращает нулевой код: связанной ветки для удаления нет. Main worktree защищён от удаления.

Обычное удаление использует правила `git worktree remove`: ignored-файлы сами по себе могут не препятствовать удалению. `--yes` не добавляет никакой защиты сверх правил Git.

**Пример `.worktree-config`:**
```text
# === Ссылки (Shared Resources) ===
# Просто имя файла = LINK (симлинк)
scripts
LINK .geminiignore

# === Копии (Independent Configs) ===
# Копируем .env, чтобы в каждом ворктри можно было менять переменные,
# не ломая настройки в других папках.
COPY .env

# === Действия (Actions) ===
# Устанавливаем зависимости сразу после создания
RUN npm install
```

> **Примечание:** Также автоматически создаются симлинки для всех файлов, перечисленных в `.git/info/exclude` (локальный игнор-лист git), если они существуют в основном репозитории.

### Переменные окружения

`wt new` читает следующие переменные. Источники в порядке приоритета: переменная окружения → `.env.local` → `.env` (оба файла — в main worktree). Из dotenv-файлов читаются только переменные с префиксом `WT_*`.

| Переменная | Описание | По умолчанию |
| :--- | :--- | :--- |
| `WT_BASE_DIR` | Куда складывать новые worktrees. Поддерживает `~`. | `../<имя-папки>` |

Пример `.env.local` в main worktree:
```bash
WT_BASE_DIR="$HOME/wt/myproject"
```

## Установка

### Глобальная установка (рекомендуется)
Клонируйте репозиторий и привяжите CLI:
```bash
git clone https://github.com/vladislavlozhkin/worktree-utils.git ~/.worktree-utils
mkdir -p ~/bin
ln -sf ~/.worktree-utils/scripts/wt ~/bin/wt
```
Убедитесь, что `~/bin` есть в `PATH`. После этого `wt` доступен из любого git-репозитория.

### Установка в конкретный проект
Чтобы добавить утилиты прямо в репозиторий (например, чтобы коммитить их вместе с командой), выполните в корне проекта:
```bash
curl -fsSL https://raw.githubusercontent.com/vladislavlozhkin/worktree-utils/main/install.sh | bash
```
Это создаст папку `scripts/` с утилитами и файл `.worktree-config`.

> Если вы скептически относитесь к `curl | bash` — сначала откройте `install.sh` глазами, а потом запустите.

## Пример Workflow

```bash
# 1. Начать новую задачу
wt new feature/awesome-bot

# 2. (Внутри папки) Если изменили конфиги или нужно пересобрать
wt setup

# 3. Посмотреть, где мы (со статусом и ahead/behind)
wt list

# 4. Завершить работу (удалить папку и ветку)
wt rm feature/awesome-bot -D
```

## Разработка

```bash
# Линтинг
shellcheck -x scripts/wt scripts/wt-* scripts/wt-lib.sh install.sh

# Smoke-тесты (создают временный git-репо в /tmp)
tests/run.sh
```
